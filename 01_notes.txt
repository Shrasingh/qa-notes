1️⃣ Google Drive via OAuth2 Streaming
✅ What it is
OAuth2 → secure way to access Google Drive without storing passwords
Streaming upload → sending the PDF directly from memory instead of saving it to disk first
✅ Why we need it
Problems we wanted to avoid:
❌ Storing PDFs on server disk (not scalable)
❌ Hardcoding Google credentials (security risk)
❌ Upload delays blocking user response
OAuth2 + streaming solves all three.
✅ How we use it in our application
Flow in your system:
Backend generates PDF in memory (Buffer)
Convert Buffer → stream
Upload directly to Google Drive using OAuth2
Decide Drive folder based on storeCode
Return PDF to user immediately
Key point:
👉 PDF never touches the server filesystem
🧠 Interview one-liner
“We upload PDFs to Google Drive using OAuth2 with streaming so files are securely stored without writing to disk, making the system scalable and cloud-friendly.”
2️⃣ Ephemeral Caching with TTL
✅ What it is
Ephemeral cache → temporary in-memory storage
TTL (Time To Live) → data auto-expires after a fixed time
In your case:
Invoice data lives for ~1 hour, then disappears
✅ Why we need it
Invoice data is:
Needed for preview
Needed for PDF generation
❌ NOT permanent business data
Saving everything to DB would:
increase load
slow down invoice flow
store unnecessary temporary data
✅ How we use it in our application
Exact flow:
Frontend sends invoice data → /api/invoice/save
Backend stores it in cache using slug as key
PDF generation fetches invoice using same slug
Cache auto-cleans after TTL
No DB involved for this flow.

🧠 Interview one-liner

“Invoice data is cached temporarily with TTL to support fast PDF generation while avoiding unnecessary database writes.”

3️⃣ Scalable PDF Generation Pipeline

(Node.js + Express + Puppeteer)

This is your strongest design point 💪

✅ What it is

A backend pipeline that:

loads a frontend route

renders it fully

exports it as a PDF

Using:

Node.js → runtime

Express → API orchestration

Puppeteer → headless browser rendering

✅ Why we need it

Main problem:

PDFs must look exactly like the UI

Maintaining separate backend templates is error-prone

This approach guarantees:

same UI

same CSS

same data

same layout

✅ How we use it in our application

Your actual flow:

Frontend builds invoice UI (/internal-invoice/:slug)

Backend opens this route using Puppeteer

Waits for:

API calls

React rendering

fonts

Exports pixel-perfect PDF

Sends PDF to user + uploads to Drive

This scales because:

logic is reusable

frontend changes auto-reflect in PDFs

no duplicate code paths

🧠 Interview one-liner

“We generate PDFs by rendering live frontend routes using Puppeteer, which guarantees visual consistency and avoids maintaining duplicate backend templates.”

🔗 How ALL THREE Work Together (VERY IMPORTANT)

Here’s the mental diagram you should remember:

Frontend Invoice UI
        ↓
Ephemeral Cache (TTL)
        ↓
Puppeteer renders UI
        ↓
PDF generated in memory
        ↓
OAuth2 Streaming upload to Google Drive
        ↓
PDF returned to user

🎯 Final 60-Second FAANG Explanation (MEMORIZE THIS)

“Invoice data is stored temporarily using an in-memory cache with TTL since it’s only needed for preview and PDF generation.
The backend uses Puppeteer to render the actual frontend invoice page into a pixel-perfect PDF, avoiding duplicate templates.
The generated PDF is uploaded securely to Google Drive using OAuth2 streaming, without writing files to disk, and returned immediately to the user.”

# march 3 A production issue surfaced a deeper architectural flaw: our identifier was encoding behavior.

We process ~1,200 invoices/day.
~25% are QuoteSheets triggered by customer reversals or pre-sale adjustments.

QuoteSheets were generated by prefixing the slug:

QS_<original_slug>

At scale, this created systemic failure modes:

slug was UNIQUE in MySQL. Under concurrent retries or double-clicks, logically identical transactions produced distinct rows.

Google Drive routing relied on slug.startsWith("QS_"), misrouting ~300 PDFs/day into incorrect folders and breaking reconciliation workflows.

Admin tooling treated slug as the canonical key, making sales and quotes indistinguishable.

I detected this while investigating reconciliation mismatches between Drive and database counts.

Constraints:

Historical slugs could not change.

Writes had to remain idempotent under retry and partial failure.

Folder routing required deterministic behavior.

The fix required more than renaming:

Made slug immutable and behavior-agnostic.

Introduced invoice_type = QS | INV.

Added an application-level idempotency guard to prevent duplicate writes under concurrent submission.

Backfilled and reconciled historical QS_ rows into canonical records.

Added monitoring to detect divergence between DB and Drive counts.

Routed storage strictly via invoice_type.

Applied QS_ only at the presentation layer (PDF filename).

Impact:

Eliminated duplicate logical documents.

Corrected 100% of misrouted QuoteSheet PDFs (~300/day).

Removed manual reconciliation overhead for operations.

Established a single canonical transaction invariant across systems.

Separating identity from behavior hardened the system against retries, concurrency, and partial failures.

Where else have you seen identifiers accumulate hidden state that eventually leaks into system behavior?
