What is a Webhook?

A webhook is a way for one system to automatically notify another system when an event happens.

Instead of you repeatedly asking:

“Has the document been signed?”
“Has the document been viewed?”

The external system (Adobe) pushes the update to you automatically.

Think of it like:

Polling = You keep calling Adobe asking “Done? Done? Done?”
Webhook = Adobe calls you when it’s done.

Why Webhook is Required in E-Sign?

In Adobe Acrobat Sign:

Once you send a document for signature:

Customer may sign in 2 minutes

Or after 2 hours

Or after 2 days

You don’t know when.

Without webhook:

You would need to constantly check Adobe API

That wastes resources

It increases complexity

It does not scale

With webhook:

Adobe notifies your backend instantly

Your system updates automatically

This gives real-time visibility.

How It Works in Adobe E-Sign Flow
Step 1 – You Send Agreement

Your backend calls Adobe API to create agreement.

Adobe returns:

agreementId

Now document is in “IN_PROCESS” state.

Step 2 – You Register Webhook

You tell Adobe:

“When anything changes for this agreement, call this URL.”

Example:

POST https://yourdomain.com/api/esign/webhook


Adobe stores that endpoint.

Step 3 – Event Happens

Customer:

Opens document → status: viewed

Signs document → status: signed

All parties complete → status: completed

At that moment:

Adobe sends HTTP POST request to your backend.

Example payload:

{
  "event": "AGREEMENT_COMPLETED",
  "agreementId": "123ABC",
  "status": "SIGNED"
}


Your backend receives this instantly.

How It Captures the Sign Process

When webhook hits your server:

Your backend:

Verifies request (security check)

Extracts agreementId

Calls Adobe API:
GET /agreements/{agreementId}/combinedDocument

Downloads signed PDF

Stores it in database or file storage

Updates invoice status to "Signed"

Now your system reflects reality immediately.

1️⃣ Asynchronous Processing
What it means

Work does not happen immediately.
You trigger something.
The result comes later.

In e-sign example

You send document for signature.
Customer signs after 2 hours.
Your system must wait.

It cannot block the server for 2 hours.

So:

You send request.

Adobe processes it.

Later you receive webhook.

That is asynchronous.

Why FAANG cares

Because real systems are never instant.
Payments, emails, uploads, ML jobs — all are async.

If you understand async → you understand scalable systems.

Memory line:

Request now. Result later.

In Adobe e-sign

Why FAANG cares

3️⃣ Idempotency (Very Important)

This is a favorite FAANG question.

What it means

If same request comes multiple times,
result should remain same.

No duplicate side effects.

Why needed in webhooks

Adobe may send webhook twice:

Network glitch

Timeout

Retry logic

If your system blindly processes twice:

You may store duplicate signed PDFs

You may update invoice twice

You may send duplicate emails

That is bad.

How to handle

Store agreementId + eventId in DB.

Before processing:

Check if already processed.

If yes → ignore.

If no → process and mark as done.

That makes system safe.

Memory line:

Same input. Same result. No double action.

4️⃣ Security Verification (HMAC Signature Validation)

Very important for production systems.

Problem

Anyone can send fake POST request to:

/api/esign/webhook


They could pretend:
“Document signed.”

That is dangerous.

Solution

Adobe sends webhook with cryptographic signature header.

Example:

X-Adobe-Signature: abc123hash


Your backend:

Uses shared secret key

Recalculates hash

Compares values

If match → valid
If not → reject request

This is HMAC validation.

Why FAANG cares

Because:

Security awareness

Prevents fraud

Protects system integrity

Memory line:

Trust, but verify.

5️⃣ Retry Handling
What happens

If your server is down or slow,
Adobe retries webhook delivery.

Maybe:

After 5 minutes

Then 10 minutes

Then 30 minutes

Why this matters

If your system is not idempotent:
Retries will break it.

Good system design:

Handles duplicate safely

Logs failures

Responds 200 quickly

Processes heavy work asynchronously

Best practice:

Return 200 OK immediately

Process work in background queue

That is production-grade design.

Memory line:

Systems fail. Design for failure.

3️⃣ Interviewer:

How do you secure your webhook endpoint?

Your Answer:

I validate HMAC signature using shared secret.

Steps:

Extract signature from request header.

Recalculate hash using payload + secret.

Compare using constant-time comparison.

Reject if mismatch.

Additionally:

Only allow HTTPS.

Restrict IP range if supported.

Log all failed verification attempts.

Because my endpoint is idempotent, retries are safe.

I monitor webhook failures.

Use alerting if repeated failures occur.

Store failed events in dead-letter queue for manual inspection.

System is designed assuming failures will happen.
