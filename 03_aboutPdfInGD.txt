💣 FAANG Interview Questions
❓ Q1: Can concurrency exist without parallelism?
✅ Answer:

Yes. On a single-core CPU, tasks are interleaved using context switching, achieving concurrency without true parallel execution.

❓ Q2: Can parallelism exist without concurrency?
✅ Answer:

Not really. Parallelism is a subset of concurrency where tasks are executed simultaneously.

❓ Q3: What does Node.js use?
✅ Answer:

Node.js uses concurrency via an event loop, not true parallelism (unless using worker threads).

❓ Q4: Why is concurrency important?
✅ Answer:

It improves responsiveness and resource utilization, especially for I/O-bound tasks.

But once I started thinking like a backend engineer, the real questions began.

🔎 What happens if 500 users generate PDFs at the same time?

Launching a Chrome instance per request is expensive.
Memory explodes. CPU spikes. System crashes.

That’s when I learned:

Why browser pooling matters

Why queue-based worker architecture is necessary

Why backpressure is not optional

🔁 What happens if a user double-clicks “Save”?

Without idempotency:

Duplicate invoices

Double inventory reduction

Multiple Drive uploads

So I explored:

Idempotency keys

Database-level unique constraints

State-based processing (PENDING → GENERATED → UPLOADED)

🔐 What happens if Google Drive rate-limits us?

Drive returns 429.

If we retry immediately?
We amplify the failure.

Instead:

Exponential backoff

Retry with jitter

Bounded queues

Proper monitoring

The feature wasn’t “Generate PDF.”

The real system was:

Client
→ API
→ Cache
→ Worker
→ Headless Browser

Every arrow represents a potential failure.

If I were to scale it to millions of invoices per day, I would:

Replace in-memory cache with Redis

Introduce Kafka/SQS for job processing

Run Puppeteer in isolated worker clusters

Move storage to object storage with CDN

Add observability and tracing

Make every operation idempotent

LinkedIn- Generating a PDF is not a feature. It is a distributed system boundary.

I recently built an invoice pipeline that renders PDFs via Puppeteer, uploads them to Google Drive, routes them to store-specific folders, and persists invoice data transactionally in MySQL.

The hard part was not rendering HTML. It was correctness under concurrency and partial failure.

Constraints:

Burst traffic (hundreds of invoices in parallel)

External dependency with rate limits (Google Drive)

Financial data requiring transactional integrity

Retry-prone clients (double clicks, timeouts)

The naive approach — “generate → upload → respond” — fails quickly:

One Chrome instance per request exhausts memory under load.

Retries create duplicate invoices and double inventory deductions.

Immediate retries on 429 amplify upstream failures.

Design decisions:

Moved PDF generation behind a bounded queue with worker isolation to control concurrency.

Enforced idempotency using unique constraints + request keys to make commits safe under retries.

Modeled invoice lifecycle explicitly (PENDING → GENERATED → UPLOADED) to handle partial failures.

Added exponential backoff with jitter for Drive uploads to prevent retry storms.

Signal I would want highlighted in feedback:
Understood that “exactly once” is achieved through idempotency + state transitions, not hope.

At modest scale, this reduced duplicate writes to zero and prevented cascading failures during load spikes.

Question: how would you evolve this design to support multi-region consistency without sacrificing write latency?
