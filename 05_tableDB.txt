🔥 PART 1 — Khan-Sir Style Explanation (Simple + Clear)

Imagine your system like a 4-step pipeline:

User → Frontend → Backend → Database → PDF + Google Drive

Let’s walk step by step.

🧠 STEP 1 — Frontend (React + Redux)

User fills the invoice form.

All data is stored in:

Redux store (formSlice)

So at any moment:

Items

Payments

Customer info

Delivery

Signatures

are inside the Redux state.

When user clicks:

Save Your Sale

This function runs:

handleCommit()
What handleCommit does:

Normalizes numbers (important for consistency)

Sends POST request:

POST /api/invoice/save

with:

{
  slug: "SUNIL_202602261700",
  form: { full invoice object }
}

So frontend responsibility:
✔ Validate
✔ Normalize
✔ Send full state
✔ Open PDF after success

Frontend does NOT:
❌ Generate PDF
❌ Save to DB directly

Clean separation.

🧠 STEP 2 — Backend Route /api/invoice/save

When backend receives:

slug + form

Two things happen:

1️⃣ Save to in-memory cache
saveInvoice(slug, form)

This stores invoice temporarily in a Map with TTL (1 hour).

Why?

Because when PDF route is called immediately after, it reads from cache for speed.

⚡ Cache = Fast
💾 DB = Persistent

2️⃣ Save to MySQL database

You insert into:

invoices_archive
Structure:
slug VARCHAR UNIQUE
invoice_type VARCHAR
editable BOOLEAN
form_json LONGTEXT

You store:

JSON.stringify(form)

So entire invoice is stored as JSON.

This gives:

✔ Schema flexibility
✔ No need for 40 relational tables
✔ Easy restore
✔ Version-safe

🧠 STEP 3 — Generate PDF

Frontend opens:

/api/invoice/pdf/:slug

Backend:

Reads invoice from cache

Determines folder (based on seller storeCode or QS)

Calls:

generatePdfFromUrl()

Which:

Launches Puppeteer

Loads frontend invoice page

Waits for rendering

Converts to PDF buffer

Then:

Uploads to Google Drive

Sends PDF to user

So flow is:

React page → Puppeteer loads same React page → PDF → Drive → User download

Smart reuse. No duplicate template.

🧠 STEP 4 — Archive Search (QS Only)

You built:

GET /api/invoice/archive/search?q=SUNIL

This searches:

WHERE invoice_type = 'QS'
AND slug LIKE '%SUNIL%'

So QuoteSheet is searchable.

🔥 Why MySQL JSON (LONGTEXT) Instead of Relational Tables?

If you had normalized tables:

invoice

invoice_items

invoice_payments

invoice_packages

invoice_signatures

invoice_delivery

It would:
❌ Increase complexity
❌ Require migrations for every new field
❌ Break older invoices

Instead you used:

form_json LONGTEXT

Benefits:

✔ Flexible schema
✔ Backward compatible
✔ Faster development
✔ No migration needed for UI changes

Tradeoff:

❌ Harder to run analytics queries
❌ Cannot easily query inside JSON fields (unless using MySQL JSON type)
❌ Not strongly structured

But for:

📄 Invoice archival system

This is PERFECT.

Because invoices are write-once, read-rarely.

Upsert to MySQL archive table

ON DUPLICATE KEY UPDATE

Because slug is unique.

So invoice is idempotent.

This prevents duplicate writes.
