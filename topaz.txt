1️⃣ Interview-Ready Answer: Why Redux-Persist Is Used

Answer:

Redux-Persist is used to persist Redux state into browser storage so that the application state is not lost on page refresh. It improves user experience by rehydrating the state automatically when the app reloads, avoiding unnecessary re-fetching or re-entering data.

2️⃣ Interview-Ready Answer: What Redux-Persist Provides

Answer:

Redux-Persist provides client-side state persistence, automatic rehydration, storage abstraction (localStorage, sessionStorage), and selective persistence using whitelists and blacklists. It is mainly useful for preserving UI and session-related state.

3️⃣ Interview-Ready Answer: How Redux-Persist Is Implemented

Answer:

Redux-Persist is implemented by wrapping the Redux reducer with persistReducer, configuring a storage engine, and delaying app rendering using PersistGate until the persisted state is restored. On refresh, Redux-Persist rehydrates the stored state into Redux automatically.

4️⃣ Interview-Ready Answer: Why Redux-Persist Is Not Suitable for Business-Critical Data

Answer:

Redux-Persist stores data locally per device, which makes it unsuitable for business-critical or multi-user data. In scenarios like multiple salespeople entering data from different machines, each device maintains its own isolated state, resulting in data inconsistency, lack of synchronization, and no central source of truth.

5️⃣ Interview-Ready Answer: What Data Should Be Persisted

Answer:

We should persist non-critical, user-specific, UI-related state that improves user experience but does not affect business correctness.

Examples:

Authentication tokens (with expiry handling)

User preferences (theme, language)

UI state (sidebar open/closed)

Form drafts or temporary input

Cached read-only API responses

✔ Low risk
✔ User-specific
✔ Easy to recover

6️⃣ Interview-Ready Answer: What Data Should NOT Be Persisted

Answer:

We should not persist business-critical, shared, or authoritative data that requires consistency, validation, or real-time accuracy.

Examples:

Sales transactions

Orders and payments

Inventory counts

Financial records

Multi-user shared data

❌ Leads to data inconsistency
❌ Cannot be trusted as a source of truth
❌ Not scalable or secure

7️⃣ Interview-Ready Architecture Justification

Answer:

Redux-Persist should be treated as a client-side optimization tool, not a data persistence layer. Business data must always be persisted on the backend where it can be validated, synchronized, audited, and shared across users.

🎯 MAANG SDE-1 Interview Questions (Q&A Format)
1️⃣ Q: Why use useEffect with cleanup in this component?

Answer:
Because hardware capture must start when component mounts and stop when it unmounts. Cleanup prevents memory leaks and device lock. It ensures resource lifecycle is tied to UI lifecycle.

2️⃣ Q: Why do we check NumberOfTabletPoints() before getting image?

Answer:
To validate that user actually signed. Without this check, we may store empty images. This is input validation at device level.

3️⃣ Q: What problem does retry() solve?

Answer:
Hardware or service APIs may fail temporarily. Retry improves resilience and handles transient failures.

4️⃣ Q: What happens if stopTopaz() is not called?

Answer:
Tablet may remain locked, memory leak may occur, and future signature sessions may fail.

5️⃣ Q: Why wrap GetSigImageB64 inside a Promise?

Answer:
Because it uses callback style API. Wrapping in Promise makes it compatible with async/await and improves readability.

6️⃣ Q: What is defensive programming in this code?

Answer:

Checking window.SetTabletState exists

Checking canvas is not null

Checking ctx exists

Checking pen points exist

This prevents runtime crashes.

7️⃣ Q: How would you make this production scalable?

Answer:

Move Topaz API into isolated service layer

Add global error logging

Add telemetry

Add signature timeout

Encrypt Base64 before sending to backend

Store signature hash for audit

8️⃣ Q: What are potential race conditions here?

Answer:
If component unmounts while getTopazImage is running, it may try updating state on unmounted component. We could fix using mounted flag or AbortController.

9️⃣ Q: How would you test this?

Answer:

Mock window.SetTabletState

Mock GetSigImageB64

Simulate no pen points

Test retry behavior

Test unmount cleanup

In my current full-time role, I integrated a Topaz digital signature pad into a production POS and order-management system handling real customer transactions and multi-step approvals.

On paper, the flow was simple:

Mount component → Capture signature → Export Base64 → Store.

In reality, it was a 5-layer system:

Pen touches tablet
→ Hardware captures coordinate + pressure data
→ SigWeb OS-level service processes input
→ JavaScript bridge exposes global APIs
→ React renders canvas + stores signature

If one layer failed, the entire system failed.

This wasn’t a frontend feature.
It was a browser ↔ OS service ↔ hardware reliability boundary.

The first version worked locally.

It failed in beta.

• Intermittent signature drops
• Tablet lockups until browser refresh
• VM deployments behaving inconsistently
• Silent HTTPS mismatches blocking SigWeb calls
• Users clicking “Apply” without pen input

Nothing crashed — which made it dangerous.

The core issue wasn’t React.

It was lifecycle misalignment.

We treated a hardware device like a UI component.

Hardware has state.
Hardware needs deterministic start/stop.
Hardware must be released explicitly.

So I redesigned the integration from first principles.

What changed:

• Mapped React mount/unmount directly to device start/stop
• Ensured only one active hardware session at a time (prevented device contention)
• Built a dedicated controller layer isolating hardware calls (Adapter pattern)
• Wrapped callback-based APIs into Promises for async/await control
• Added bounded retry logic to handle transient VM / USB timing instability
• Introduced proactive health checks for SigWeb service availability
• Validated NumberOfTabletPoints before exporting image (device-level input validation)
• Translated low-level hardware errors into clear user-facing messages

We then validated against real-world instability:

• VM cold boots
• USB reconnect scenarios
• Service restarts
• Rapid open/close race conditions
• Multiple signature steps in a workflow

After the redesign:

✔ No more device lockups
✔ Stable across laptops and VMs
✔ Zero post-release escalations
✔ Clean separation between UI, hardware control, and business logic
✔ Easy to extend for multi-signature workflows

The deeper lesson wasn’t about Topaz.

It was about engineering maturity.

When software crosses system boundaries — browser to OS, OS to hardware — you’re no longer writing UI.

You’re designing:

• Lifecycle synchronization
• Failure isolation
• Defensive programming
• Resource management
• Observability before optimization
• Deterministic cleanup

Correctness in ideal conditions is easy.

Reliability under imperfect environments is engineering.

This experience fundamentally changed how I debug systems:
